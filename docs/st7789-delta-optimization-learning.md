# ST7789 差分刷新优化学习笔记

本文用于学习当前工程里使用的 ST7789 GIF 动画优化方法。重点不是某一段 C
代码，而是一套嵌入式显示优化思路：

```text
先减少需要存储的数据
再减少需要发送的像素
再减少地址窗口和 DMA 启动次数
最后用统计数据决定参数
```

当前工程的显示链路是：

```text
GIF -> PC 端合成帧 -> 16 色量化 -> 4 位索引图
    -> 首帧完整保存
    -> 后续帧保存差分流
    -> STM32 解码差分流
    -> ST7789 地址窗口 + SPI2 TX DMA 发送像素
```

## 1. 为什么 STM32 不直接播放 GIF

GIF 文件不是一张张完整图片的简单集合。它可能包含：

- 局部矩形更新；
- 透明像素；
- disposal 规则；
- 每帧不同的延时；
- 调色板变化。

STM32F103C8 的 Flash 和 RAM 都很有限，不适合在单片机端解析这些格式。更稳的
方式是让电脑完成复杂工作，单片机只执行固定格式的数据刷新。

当前脚本 `Tools/generate_st7789_gif.py` 会先用 Pillow 按 GIF 规则合成每帧，
再转成固件可以直接使用的数组。

## 2. 当前数据格式

当前素材固定为 120x120，屏幕是 240x240，所以固件把每个源像素在 X 和 Y
方向各放大 2 倍。

如果直接保存 RGB565 整帧：

```text
120 x 120 x 2 = 28800 字节/帧
28 帧约 788 KB
```

这明显超出 STM32F103C8 的 Flash。当前工程改用 16 色索引：

```text
每个源像素 = 4 bit
120 x 120 / 2 = 7200 字节/帧
```

即使这样，28 帧也约 197 KB，仍然过大。所以工程只完整保存首帧，后续只保存
相邻帧之间的变化部分。

## 3. 差分流是什么

差分流的核心问题是：

```text
当前帧和上一帧相比，哪些像素变了？
```

对每一行 120 个源像素，脚本从左到右扫描，生成两类段：

```text
跳过段：这些像素没变，不发给 ST7789，继续保留屏幕显存里的旧内容
绘制段：这些像素变了，设置地址窗口并通过 SPI2 TX DMA 发新像素
```

控制字节格式是：

```text
bit7 = 1：跳过段
bit7 = 0：绘制段
bit6..0：段长度 - 1
```

绘制段后面跟随打包的 4 位颜色索引。固件解码索引后，从 16 色调色板得到
RGB565，再写入 ST7789。

## 4. 为什么段数很重要

初看会以为 SPI 刷屏只看发送了多少字节。实际不是这样。

每个绘制段都需要：

```text
等待前一次 DMA 完成
发送 CASET 列地址命令
发送 RASET 行地址命令
发送 RAMWR 写显存命令
切换 DC 引脚
准备 DMA 缓冲
启动一次 DMA
等待 DMA 完成中断
```

因此性能由两部分共同决定：

```text
像素字节数：真正通过 SPI 发出的 RGB565 数据量
段数：地址窗口设置次数和 DMA 启动次数
```

如果段很碎，哪怕像素字节少，控制开销也会很大。

## 5. 短空洞合并

严格差分只刷新真正变化的像素。例如一行里有这种情况：

```text
变 变 不变 变 变
```

严格编码会产生两个绘制段：

```text
绘制 2 像素
跳过 1 像素
绘制 2 像素
```

这会带来两次地址窗口和两次 DMA。短空洞合并会把中间很短的不变像素也一起
刷新：

```text
绘制 5 像素
```

画面不会变，因为中间那个像素发的是它原本已经显示的颜色。代价是多发一点
像素数据，收益是减少绘制段数量。

脚本参数：

```text
--merge-gap 0：完全严格，不合并短空洞
--merge-gap 1：合并 1 个源像素空洞，当前默认值
--merge-gap 2：合并 2 个以内源像素空洞
--merge-gap 4：合并 4 个以内源像素空洞
```

## 6. 怎么看统计数据

运行：

```powershell
py -B Tools\generate_st7789_gif.py --stats-only --compare-gaps 0,1,2,4
```

当前小猫 GIF 的统计结果是：

```text
merge_gap=0: delta_bytes=56291, draw_runs=14049, skip_runs=17409, dma_bytes=329056, draw_source_pixels=41132, min_run=1, max_run=30, small_runs=11495
merge_gap=1: delta_bytes=49109, draw_runs=10101, skip_runs=13461, dma_bytes=360640, draw_source_pixels=45080, min_run=1, max_run=50, small_runs=6169
merge_gap=2: delta_bytes=45922, draw_runs=7704, skip_runs=11064, dma_bytes=398992, draw_source_pixels=49874, min_run=1, max_run=53, small_runs=3279
merge_gap=4: delta_bytes=44392, draw_runs=5353, skip_runs=8713, dma_bytes=462360, draw_source_pixels=57795, min_run=1, max_run=71, small_runs=1345
```

字段含义：

- `delta_bytes`：最终写进 Flash 的帧差字节数。
- `draw_runs`：绘制段数量，大致对应地址窗口设置次数和 DMA 启动次数。
- `skip_runs`：跳过段数量。
- `dma_bytes`：估算的 RGB565 像素 DMA 字节数，已经考虑 2 倍放大。
- `draw_source_pixels`：被刷新的源像素数量。
- `min_run` / `max_run`：最短和最长绘制段长度。
- `small_runs`：小于等于 `--small-run-limit` 的短绘制段数量。

这些数据说明：

```text
merge_gap=0 段数最多，像素字节最少。
merge_gap=1 是当前默认，Flash 和段数都有明显改善。
merge_gap=2 段数继续下降，像素字节适度增加。
merge_gap=4 段数下降很多，但像素字节增加也明显。
```

所以 `merge_gap=2` 是下一步比较值得实机测试的候选点。

## 7. 怎么选择 merge_gap

不要只看一个指标。建议按下面顺序判断：

1. 先看 `draw_runs` 是否明显下降。
2. 再看 `dma_bytes` 是否增加过多。
3. 再看 `delta_bytes` 是否影响 Flash 空间。
4. 最后上板实测是否更流畅。

经验判断：

```text
如果 draw_runs 大幅下降，dma_bytes 小幅上升，值得尝试。
如果 draw_runs 小幅下降，dma_bytes 大幅上升，不值得。
如果 delta_bytes 超出 Flash，不能用。
```

当前小猫 GIF：

```text
merge_gap=1 -> draw_runs 10101，dma_bytes 360640
merge_gap=2 -> draw_runs 7704，dma_bytes 398992
```

段数减少约 24%，像素字节增加约 11%。这通常值得实测。

## 8. 这套方法有通用性吗

有通用性，但不是所有 GIF 都同样受益。

适合这套方法的素材：

- 背景大部分不变；
- 主体在局部移动；
- 像素风、图标、表情包、小动画；
- 相邻帧变化区域相对集中；
- 颜色数量不多。

收益较小的素材：

- 全屏闪烁；
- 大面积渐变移动；
- 摄影视频类 GIF；
- 每帧都有全屏噪点；
- 抖动或 dithering 很重的 GIF。

原因是差分优化依赖“上一帧显存可以复用”。如果每一帧几乎全屏都变了，差分
就接近整帧刷新，段合并也救不了太多。

## 9. 换 GIF 时要注意什么

当前 `generate_st7789_gif.py` 是为这个工程的 ST7789 小猫动画定制的。它目前
假设：

```text
输入 GIF 尺寸必须是 120x120
保留 28 帧
每帧间隔 40 ms
输出放大 2 倍到 240x240
使用 16 色 RGB565 调色板
```

所以如果你直接换 GIF，最稳的是先把 GIF 处理成：

```text
120x120
帧数接近或大于 28
动作用 40 ms 左右观察合理
颜色不要太复杂
```

然后运行：

```powershell
py -B Tools\generate_st7789_gif.py --stats-only --compare-gaps 0,1,2,4
```

看统计结果。如果默认 `merge_gap=1` 合理，再生成：

```powershell
py -B Tools\generate_st7789_gif.py
```

如果要试 `merge_gap=2`：

```powershell
py -B Tools\generate_st7789_gif.py --merge-gap 2
```

生成后重新编译烧录，观察是否更流畅、是否有错位或残留。

## 10. 换不同尺寸或屏幕时怎么迁移

方法本身可以迁移，具体参数需要改。

如果还是 ST7789，但素材尺寸不同，需要统一这些量：

```text
源图宽高
目标屏幕宽高
缩放倍数
颜色格式
帧数
帧间隔
Flash 上限
RAM 行缓冲大小
```

如果换成 128x64 单色 OLED，方法仍然类似：

```text
首帧完整保存
后续帧保存差分
跳过未变化区域
合并短空洞减少命令次数
用统计数据比较参数
```

但数据格式会完全不同。SSD1306 是页格式单色数据，不是 RGB565，也不是 ST7789
的地址窗口像素流。

## 11. 学习这类优化的思路

这类优化不是先写复杂代码，而是按层拆问题：

```text
存储层：Flash 是否放得下？
传输层：SPI 要发多少字节？
控制层：地址窗口和 DMA 启动有多少次？
调度层：主循环是否被长期阻塞？
恢复层：数据损坏后能否回到已知状态？
```

当前工程对应的答案是：

```text
Flash：首帧 + 差分流
SPI：只发变化段
控制：merge_gap 减少碎段
调度：异步差分状态机 + DMA 完成中断
恢复：差分流错误后重画首帧
```

以后遇到别的显示项目，也可以按这个顺序分析。

## 12. 推荐实验路线

建议这样学习和验证：

1. 先运行统计命令，不改固件：

   ```powershell
   py -B Tools\generate_st7789_gif.py --stats-only --compare-gaps 0,1,2,4
   ```

2. 记录每个参数的 `draw_runs`、`dma_bytes`、`delta_bytes`。

3. 选择一个候选值，比如 `merge_gap=2`。

4. 生成数组：

   ```powershell
   py -B Tools\generate_st7789_gif.py --merge-gap 2
   ```

5. Keil 重新编译并烧录。

6. 观察：

   ```text
   动画是否更流畅
   是否有花屏
   是否有残留
   循环边界是否正常
   复位后是否能从首帧恢复
   ```

7. 如果效果更好，再考虑把默认值从 1 改成 2。

## 13. 当前不建议先做的事

不建议先做这些：

- 为 ST7789 加 SPI RX DMA：当前模块没有 MISO，没意义。
- 加全屏 RGB565 帧缓冲：F103C8 RAM 不够。
- 把 ST7789 命令也 DMA 化：复杂度高，收益小。
- 直接把 `merge_gap` 调很大：可能多发太多像素，抵消段数减少收益。
- 不看统计直接调参数：容易把 Flash 或 SPI 带宽用在无效刷新上。

## 14. 一句话总结

这套方法的本质是：

```text
用上一帧的屏幕显存当隐式缓存，只发送变化区域；
再用短空洞合并减少碎片化；
最后用统计数据在“少发像素”和“少开窗口”之间找平衡。
```
